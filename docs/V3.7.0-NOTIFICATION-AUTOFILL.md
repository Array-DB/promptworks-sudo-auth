# PromptWorks v3.7.0 — notification + automatic PAM response

v3.7.0 keeps the protected side-by-side upgrade model and changes runtime sudo approval from manual decision-code entry to a bound local-backend transaction.

## Runtime flow

1. The existing OS sudo/PAM stack completes first.
2. `pam_promptworks.so` starts the root-owned runtime bridge.
3. The bridge creates a 60-second request on the paired HTTPS backend.
4. PAM prints the request's 3-digit number match.
5. The v3.7 APK foreground listener sees the pending request and posts a high-priority notification.
6. Tapping the notification opens PromptWorks; the same 3 digits, host and command are shown without a scrolling runtime screen.
7. APPROVE or DENY requires `BIOMETRIC_STRONG` and the Android hardware-backed approval key signs the decision.
8. PAM receives the backend result automatically. No 8-digit code is typed by the user.
9. The terminal prints only a masked receipt (`****1234` style) so the full receipt is not exposed.

## Side-by-side package

The v3.7 APK uses `com.promptworks.sudoauth.secure.v37`, so it can be installed alongside `com.promptworks.sudoauth.secure` and older PromptWorks packages.

## Upgrade rollback rule

During migration, the installer snapshots the currently active PromptWorks PAM file, PAM module and binding. Automatic upgrade rollback prefers this snapshot. In other words, an unsuccessful v3.7 migration restores the previous PromptWorks backend/PAM binding; it does **not** intentionally switch an already-protected upgrade back to the distro/original sudo mode.

## Network note

The local PromptWorks HTTPS backend remains running after provisioning in v3.7. The phone must be able to reach that bound backend for notification and decision delivery. The approval decision is still authenticated by the enrolled phone's hardware-backed signing key.
